Cómo se hizo el proyecto

El proyecto "Editor de Procesos" fue desarrollado siguiendo una metodología ágil (Scrum) dividida en 3 Sprints estratégicos, pactados formalmente entre el 4 y el 22 de marzo de 2026. La organización se planteó asignando de forma cruzada a un equipo técnico (7 "Devs" virtuales) labores críticas orientadas a construir el Core del Backend utilizando Java, Spring Boot y PostgreSQL.

El flujo priorizó asentar la arquitectura multi-tenant en el Sprint 1, dar vida al motor de lógica relacional BPMN (Nodos, Lanes y Arcos) en el Sprint 2 y, por último asegurar permisos robustos, mensajería y la pulcritud de código en el Sprint 3. Garantizamos la estabilidad obligando a que cualquier funcionalidad estuviera apoyada fuertemente por Pruebas Unitarias utilizando JUnit 5 y Mockito antes de combinarse con la rama principal.

Dailys

Daily 1

Fecha: 04 / 03 / 2026

Objetivos: Levantar los cimientos del sistema, definir autenticación y establecer la arquitectura base de repositorios y servicios.

Notas: Se trabajó en conjunto para montar las entidades fundamentales: Empresa y Usuario. Dev 1 y Dev 2 se encargaron del registro corporativo (HU-01) y perfiles (HU-02), mientras Dev 3 preparó un control de Autenticación. Simultáneamente se estructuraron las plantillas de Pool y Proceso iniciales.

Daily 2

Fecha: 09 / 03 / 2026

Objetivos: Primera integración profunda inter-módulos y cierre formal del Sprint 1.

Notas: Tuvimos cuellos de botella con errores "No Autorizado (403)" que no dejaban vincular procesos porque el token pasaba vacio a la validación corporativa. Se depuró en conjunto conectando el servicio de auth simulado; tras superarlo, la primera rama unificada del Sprint ingresó a Develop.

Daily 3

Fecha: 11 / 03 / 2026

Objetivos: Inicio del Sprint 2 y partición de responsabilidades para el Motor de Diagramado en base de datos.

Notas: Acordamos las dependencias mutuas: Dev 1 programaría 'Actividades', Dev 2 'Lanes', Dev 3 sus 'Gateways', y Dev 4 prepararía el terreno armando los 'Arcos' de enlace. Se dictaminó regla estricta: un Arco no puede existir si falla al validar sus puntas (origen/destino).

Daily 4

Fecha: 14 / 03 / 2026

Objetivos: Arreglos a mitad del Sprint 2 y discusión arquitectónica sobre conflictos en la ramificación.

Notas: Tuvimos cruces de código entre la creación de Lanes y Actividades por reescribir inyecciones ajenas. Tras esto surgió el reto de la fase: el borrado. Si un backend borra un Gateway y este poseía Arcos trazados, se generaban líneas de código "huérfanas" y corruptas. Pactamos el proceso defensivo de "Saneamiento cruzado" inyectando cascadas en BD.

Daily 5

Fecha: 17 / 03 / 2026

Objetivos: Comprobación de aseguramiento de calidad y despliegue del Sprint 2.

Notas: Detectamos omisiones simples (falta del DELETE seguro para Lanes si poseía contenido interno), por lo que se resolvieron rápidamente de forma preventiva. Con un pull request masivo cerramos todo el lienzo y sus validaciones en la base de PostgreSQL, pasando todas las pruebas pactadas.

Daily 6

Fecha: 18 / 03 / 2026

Objetivos: Arranque de Sprint 3. Foco absoluto en la mensajería, eventos y sistemas de roles duros.

Notas: Tres Devs se adueñaron de los eventos BPMN (Throw, Catch, Correlación). Crearon la lógica `correlateMessages` enlazando las rutinas mediante `businessKey`.

Daily 7

Fecha: 20 / 03 / 2026

Objetivos: Resolución de incidencias tras implementar el robusto sistema de Permisos.

Notas: Al incluir las clases `PermisosPoolService` que prohibían drásticamente acciones a los perfiles tipo 'Lector', reventamos masivamente 11 de nuestras Suites de Testing arrojando `NullPointerExceptions` en todos lados. La banda paró labores funcionales y todos ayudamos al equipo a rehacer inyecciones puras, actualizando constructores globales.

Daily 8

Fecha: 22 / 03 / 2026

Objetivos: Pruebas Unitarias definitivas y cierre oficial del Release Candidate Fase 1.

Notas: Liderado por Dev 4, el saneamiento dio una merecida recompensa. Tras configurar adecuadamente nuestros `AssertJ` y Mocks, lanzamos una orden `mvn clean test` global. Exitosamente marcamos: **158 tests en verde (100% pase sin fallos ni errores)**. Un build perfecto en menos de un minuto nos entregó una API lista.

Conclusión del Proyecto

El desarrollo del Editor de Procesos concluye con un backend robusto, escalable y altamente estabilizado. A lo largo de los tres Sprints, la sinergia del equipo y la metodología ágil fueron cruciales para superar desafíos técnicos complejos; desde garantizar la consistencia relacional del grafo BPMN y manejar el borrado en cascada, hasta la integración de un estricto sistema de permisos por roles. La comunicación constante en estas reuniones diarias (Dailys) nos permitió anticipar cuellos de botella y diseñar soluciones de saneamiento cruzado efectivas. Todo este esfuerzo colaborativo culmina en la entrega de una API sólida y protegida por una cobertura de pruebas excepcional (158 tests exitosos en verde), sentando bases inquebrantables de calidad y las mejores prácticas en Ingeniería de Software listas para producción.
